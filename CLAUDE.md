# CLAUDE.md

## Overview

Build Bruh UI is an Angular 22 single-page app with NgRx 22, TypeScript 6, Tailwind CSS 4 and daisyUI 5, built with the esbuild-based `application` builder (`ng serve` runs on Vite). The Angular 22 CLI needs Node ^22.22.3, ^24.15 or >=26. Builds and tests are verified on Node 26, pinned in `.nvmrc` (`nvm use`), which CI reads too (`node-version-file`). It is the frontend for the Build Bruh REST API (the sibling repo `../build-bro-api`, Spring Boot on port 8080). It browses builds, build sets, projects, servers and deployments.

## Commands

```bash
npm start              # ng serve on :4200, proxies /api -> http://localhost:8080 (proxy.conf.json)
npm run start-iso      # ng serve without the proxy
npm run build          # production build to dist/build-bro-ui/browser
npm run watch          # development build in watch mode
npm test               # Vitest unit tests in watch mode (`npm test -- --watch=false` once, add `--coverage` for coverage/)
npx ng test --watch=false --include='src/app/builds/**/*.spec.ts'   # a subset of unit specs
npm run api:update     # fetch the API contract from build-bro-api (main) and regenerate the API types
npm run api:check      # fail if the contract copy or the generated types are out of date (runs in CI)
```

No linter is configured (there is no `ng lint` target and no ESLint). npm 12 (bundled with Node 26) blocks dependency install scripts unless `package.json` → `allowScripts` approves them; none are needed (esbuild, lmdb, msgpackr-extract, @parcel/watcher and fsevents ship prebuilt binaries), so CI installs with `npm ci --ignore-scripts`. This repo has only unit tests:

- **Unit tests** (Vitest through Angular's `@angular/build:unit-test` builder, the `test` target in `angular.json`, `tsconfig.spec.json`). They run in Node with jsdom, no browser or backend, in a few seconds. Specs sit next to the code as `*.spec.ts`. They cover the logic layer (reducers, selectors, effects, guards, pipes, `ThemeService`) and the app shell (`AppComponent`, `SideNav`). Other components get unit tests as they are redesigned (epic #44). Component specs set inputs with `fixture.componentRef.setInput(...)`, wait with `await fixture.whenStable()` (zoneless), use `provideMockStore({initialState})` for pages, and find elements by `data-testid` (a `byTestId()` helper per spec). Helpers in `src/testing/`: `setUpEffects()` (effects with `provideMockActions`, `provideMockStore` selectors and `HttpTestingController`), `collect()` (what an effect emits), `API_ERROR`, small data builders (`someProjects()`, `build()`, …) and `inTimeZone()` (runs a `describe` with a pinned `TZ`, for tests of how times are shown). Test selectors through `.projector(...)`, guards with `TestBed.runInInjectionContext`. Configuring `TestBed` twice in one test fails, so use `it.each` for variations. Vitest globals (`describe`, `it`, `expect`, `vi`) need no imports.

**End-to-end tests live in [build-bro-acceptance](../build-bro-acceptance)** (Playwright against the live API, UI and database). There is no fake API and no e2e suite in this repo any more. A change to a page that breaks a user journey needs a matching change there (separate PR).

The quality gate wants 80% coverage on new code, so new logic needs unit tests. SonarCloud analyzes the whole repository (its analysis scope ignores `sonar.sources`/`sonar.tests`; only exclusions work), so `sonar-project.properties` excludes `src/**/*.spec.ts`, `src/testing/` and the generated API types from the analysis, and leaves `scripts/` and files without logic (`main.ts`, environments, `*.routes.ts`, `*.actions.ts`, the same list as `coverageExclude` in `angular.json`) out of coverage. A new file that isn't app code needs to be added there, or it counts as uncovered code. The SonarCloud project uses CI-based analysis, so its "Automatic Analysis" must stay off, or the scan fails. Unit specs and the acceptance tests find some elements by `data-testid`, so keep those attributes when editing templates (search the specs and build-bro-acceptance before removing one). New specs should prefer what a user sees (role, label, text) and use `data-testid` only where nothing else identifies an element.

## Architecture

- **Standalone components, no NgModules.** Standalone is the default since Angular 19, so components and pipes don't declare `standalone: true`. The compiler warns about components in `imports` that a template doesn't use, so remove those. `src/main.ts` bootstraps `AppComponent` with `bootstrapApplication`. The app is **zoneless** (`provideZonelessChangeDetection()`; there is no `zone.js`). Change detection runs only after template events, `async` pipe emissions, signal changes or `markForCheck()`, not after timers or plain subscriptions. So keep state flowing through the store and the `async` pipe. Buttons inside a `<form>` need an explicit `type`. A button without one is a submit button: it also fires the form's `(submit)` right after its `(click)`, before change detection has passed new inputs to the form. It also registers the root store slices (`alert`, `stats`, `nav`, `projects`, `servers`, `labels`), their effects and the store devtools with NgRx's standalone providers (`provideStore`, `provideEffects`, `provideStoreDevtools`). There are no NgModule imports (`importProvidersFrom`) and no Angular animations. `app.routes.ts` lazy-loads one `*.routes.ts` per feature folder. Dependencies are injected with `inject()` in field initializers (`private store = inject<Store<Buildz>>(Store)`), not constructor parameters. Declare them above the fields that use them, such as `createEffect(() => this.actions$...)` in effects or `this.store.pipe(...)` in pages.
- **Feature folders** (`builds/`, `build-sets/`, `build-set-edit/`, `deployments/`, `projects/`, `servers/`, `labels/`, `home/`) follow this pattern, though not every folder has every part. `projects/`, `servers/` and `home/` have no `state/` and read the root slices (`projects`, `servers`, `stats`). `build-sets/` has no `ui/` and uses `src/app/ui/build-sets/`.
  - `*.page.ts` is the routed container component. It selects from the store and dispatches actions.
  - `ui/` holds presentational components with `@Input`/`@Output`.
  - `state/` holds the NgRx actions, reducer, selectors and effects. These are registered **lazily in the feature's route `providers`** via `provideState(FEATURE_X, reducer)` / `provideEffects(XEffects)` (see `builds/builds.routes.ts`), not in `main.ts`.
- **App shell** (`app.component.ts`): the side nav (`ui/nav/side.nav.ts`: logo, main navigation with the active page marked via `aria-current`, theme switch; it collapses to icons, state in the `nav` slice) next to a centred content column (max 1120 px) with the alert panel above the routed page. The shell is a daisyUI `drawer` that is always open from Tailwind's `md` breakpoint (768 px) up, where the side nav stays in view while the page scrolls. Below it, a top bar with a menu button opens the side nav as a slide-out menu. It always shows the labels there, and it closes after choosing a page, on Escape, on the overlay or with its close button, which give the focus back to the menu button. `menuOpen` drives the drawer's checkbox; `isPhone` follows `PHONE_QUERY` with `matchMedia` (absent in jsdom, so unit tests stub it).
- **Shared code**: `src/app/ui/` holds presentational components reused across features (accordions, paginator, nav, alert panel). Pages start with `bb-page-header` (the edit page has its own header with a breadcrumb in `build-set-name.form.ts`) (`heading`, `description`, actions as content), says "nothing here" with `bb-empty-state` (`icon`, `framed` for a dashed box on the page, `compact` for side panels; message and button as content) and shows `bb-loading` while data is on its way. Use them instead of repeating the markup. Labels are shown with `bb-label-chip` (`ui/labels/label-chip.ts`): by their label definition (build-bro-api#7, root slice `labels`, loaded at start), i.e. display name, style (`badge-info`/`-success`/`-warning`/`-error`) and type (URL as link, boolean as icon); `mode="value"` shows only the value. The view logic is `labelView()` in `core/labels/label-view.ts`; `fitsDefinition()`/`violationOf()` in `core/labels/label-values.ts` check a value the way the API does; `expectedValue()`/`labelProblems()` there word the hints. The build search's label filter suggests keys (`labelKeys` from `/search-data`, loaded by the builds page, plus the definitions for builds) and makes the value follow a defined key's type (a select for enums and booleans, a hint, no adding a value that can't match); the build-set template rows point out label filters that don't fit. The `/labels` page (`labels/`, feature slice `labelAdmin`) manages the definitions: preview (`dryRun`) and save, delete, the conformance report and the `OFF`/`STRICT` validation setting. Saving or deleting dispatches the root actions `labelDefinitionSaved`/`labelDefinitionDeleted`, so the `labels` slice and every chip stay current. Components that show labels take the definitions as an input (`labelDefinitions`), which their page selects with `theLabelDefinitions`. `src/app/core/` holds the shared model interfaces (`core/state/model.ts`), root-level state slices and pipes. Import shared things through the `core/index.ts` barrel.
- **Forms use Signal Forms** (`@angular/forms/signals`, stable since Angular 22), not `ngModel` or Reactive Forms. In dev mode NgRx freezes state and actions, so no component may change an object it got from the store, and reducers and selectors build new objects with spreads. A form edits a draft: `storeDraft(() => this.input(), (value) => this.output.emit(value))` (`ui/forms/store-draft.ts`) gives a `model` (a `linkedSignal` that starts over whenever the store sends a new value) and reports every change once, without echoing the store's answer. A form that only reports on Save uses a plain `linkedSignal` and the form's `submission.action` (`BuildSetNameForm`, `ServerDetailsForm`). Signal Forms write changes as new objects, so the store's value stays untouched. Things to know:
  - **Keep the form's model flat:** only the fields the form edits. Signal Forms mark objects inside arrays to track them, which throws on frozen store objects (see `RowFields` in `build-template.form.ts`).
  - A native `<select>` binds only to text fields: bind a number or an object by hand with `(change)` (page size), or keep its key as text in the model (branch name).
  - Text inputs want `''` for empty, so a `number | null` field uses `<input type="number">`. Attributes such as `min`, `required` or `name` can't be set on a `[formField]` element; use schema rules (`min()`, `required()`).
  - `debounce(path, TYPING_PAUSE_MS)` delays typed numbers; `submit()` (Enter, Reload, Save) first takes over values that are still waiting, and a form `reset()` drops them.
  - Unit tests hand forms deep-frozen inputs (`deepFreeze` from `src/testing/freeze.ts`), so a mutation fails the test. Selects fire `input` as well as `change`, and fields that wait for blur need a `blur` event.
- **HTTP lives only in effects** (and some route guards). They call relative `/api/v1/...` URLs with `HttpClient` (`provideHttpClient(withXhr())` keeps the XHR backend, since Angular 22 defaults to `fetch`), and failures map to `AlertActions.backendErrorOccurred`. The global alert reducer reads the backend's error shape (`error.message` / `error.description`, from the API's `IExceptionInfo`).
- **Route guards load data**: in `build-set-edit`, the `new` / `:build-set-name` / `clone/:build-set-name` guards (`guards/*.guard.ts`) dispatch load actions and always return `true`; `build-sets.routes.ts` does the same for the build set names. Guards are functional `CanActivateFn`s that use `inject(Store)`, not classes (class guards are deprecated).
- **Templates are inline** and use the built-in control flow (`@if`, `@for`), not `*ngIf`/`*ngFor`. Track `@for` loops over objects by a stable key (`track build.id`, `track buildTemplate.project.id`, `track label.key` for `keyvalue`), not by the object itself. Store updates always create new objects, so tracking by identity rebuilds every row on each update. That logs NG0956 in dev mode and loses DOM state. With a stable key, Angular reuses the row's components and only passes in new inputs, so those components must render from their inputs; a copy they edit has to start over when the input changes (`linkedSignal`, see Forms). Loops over plain strings can use `track name`. They are styled with Tailwind utility classes plus daisyUI component classes. Tailwind 4 is configured in CSS, not in a `tailwind.config.js`. Angular's builder runs it through PostCSS (`.postcssrc.json` → `@tailwindcss/postcss`), and Tailwind finds the classes in the inline templates on its own. `src/styles.css` holds the whole setup:
  - The `@import`s come first (Material Icons, then the Inter, Plus Jakarta Sans and JetBrains Mono variable fonts from `@fontsource-variable/*`), because browsers ignore an `@import` after other rules. The fonts are bundled, so there are no external font requests. `@theme` maps them to `font-sans` (text, the default), `font-display` (headings; `h1`–`h3` use it automatically) and `font-mono` (build numbers, hashes).
  - `@plugin 'daisyui' { themes: false; }` turns off daisyUI's built-in themes, and three `@plugin 'daisyui/theme'` blocks define ours: **light** (default), **dark** and **lagoon** (the custom theme). Keep them in sync with `THEMES` in `core/theme.service.ts`. Colors: page background `base-200`, cards `base-100`, borders `base-300`. **Projects are never color-coded** (setups can have dozens of them); color only marks state: tests ok/broken, pinned builds, selection.
  - `ThemeService` (`core/theme.service.ts`) sets `data-theme` on `<html>` and remembers the choice in `localStorage` (wrapped in try/catch; it falls back to light). The theme switch is at the bottom of the side nav.
  - A small override keeps daisyUI's `.collapse` (the accordions) visible. Tailwind 4's `collapse` utility (`visibility: collapse`) would otherwise win over it.

  daisyUI 5 defaults that differ from daisyUI 2:
  - A plain `btn` is light grey; add `btn-neutral` for the dark buttons used throughout the app.
  - Inputs and selects are bordered without `input-bordered`/`select-bordered`.
  - Button groups are `join` + `join-item`, and the selected menu entry is `menu-active`.
  - `form-control` and `label-text` no longer exist (use `flex flex-col` and `text-sm`).
  - Tailwind 4's `border` uses the current text color, so give borders a theme color such as `border-base-content/20`. Components use `OnPush` change detection (the default since Angular 22; the two components that never set a strategy were given `ChangeDetectionStrategy.Eager`, the pre-22 default).
- **API types come from the API contract.** `api/build-bro-api.yaml` is a copy of build-bro-api's OpenAPI contract (`src/main/resources/openapi/build-bro-api.yaml`, the source of the API surface). `openapi-typescript` generates `src/app/core/api/build-bro-api.ts` from it; never edit either file by hand, run `npm run api:update` (`scripts/api-contract.mjs`; `API_CONTRACT_REF=<branch>` fetches from an unmerged API branch). `npm run api:check` runs in CI and fails when the copy differs from build-bro-api's `main` or the generated file is stale, so **merge an API contract change before the UI change that needs it**. `openapi-typescript` declares `typescript ^5.x` as peer; `package.json` → `overrides` points it at the project's TypeScript 6.
  - `core/state/model.ts` turns the generated schemas into the app's model types under the existing names (`IBuild`, `IBuildSearchParams` = `IBuildSearch`, `IBuildStats` = `IBuildBroStats`, …) and defines the UI-only types. The contract marks hardly any property as required, so the generated types are mostly optional; until that is decided in the contract, `model.ts` keeps the UI's assumptions explicitly: `Present<…>` (every property there), `WithOptional` and `WithNull` (the fields the UI sends as `null`). A renamed, removed or retyped property in the contract therefore fails the type check.
  - Timestamps (`format: date-time`, e.g. `deployedAt`) are UTC instants with a `Z` (`"2026-11-22T19:42:48Z"`, build-bro-api#15). Templates show them with date-fns (`ngx-date-fns`: `dfnsParseIso | dfnsFormat`/`dfnsFormatDistanceToNowPure`), which formats in the browser's timezone; no other date library is needed. Test data needs the `Z` too: without it `parseISO` reads the time as local.
  - Enum values are the contract's, e.g. `sortDirection: 'ASC' | 'DESC'` (the API accepts any case, the types don't).

## Deployment

**Docker image** (issue #81): `docker build .` works from a clean checkout. The multi-stage `Dockerfile` runs `npm ci --ignore-scripts` and `npm run build` on `node:26-alpine` (npm's cache in a BuildKit cache mount) and copies `dist/build-bro-ui/browser` into `nginxinc/nginx-unprivileged:<ver>-alpine-slim` (user `101`, port `8080`; the slim variant has the same entrypoint with a third of the packages). Both base images are pinned by digest; Dependabot (`docker` ecosystem) updates them. The runtime stage also runs `apk upgrade`, because upstream rebuilds lag behind Alpine's security fixes (Trivy failed on 20 fixed findings in the pinned image), so the Alpine packages depend on the build date. The nginx files are in `docker/`:

- `docker/conf.d/default.conf.template`: rendered at startup by the image's entrypoint (envsubst) into `/tmp/conf.d` (`NGINX_ENVSUBST_OUTPUT_DIR=/tmp`), so the root filesystem can be read-only with a `tmpfs` on `/tmp`. `/api/` goes to `http://${BUILDZ_API}:8080` (`BUILDZ_API`, default `api`, the only setting) through a variable in `proxy_pass`, so the host is resolved per request: the UI starts without the API and answers `502` until it is reachable. The resolver comes from `/etc/resolv.conf` (`NGINX_ENTRYPOINT_LOCAL_RESOLVERS=1`); nginx ignores search domains, so Kubernetes needs the full name. Everything else falls back to `index.html` (SPA routing). Hashed files (`-<8 chars>.<ext>`) get a one-year `immutable` `Cache-Control`, `index.html` gets `no-cache`. A template line with `${NAME}` is replaced only when the environment variable `NAME` exists; nginx's lowercase variables are safe.
- `docker/snippets/security-headers.conf`: CSP and the other security headers. nginx drops inherited `add_header`s in a block with its own, so every location that adds a header includes the snippet again.
- `docker/nginx.conf`: the base image's config plus `server_tokens off`, gzip, and the include from `/tmp/conf.d`.

**The CSP allows no inline scripts** (`script-src 'self'`). That's why the production build has critical-CSS inlining turned off (`optimization.styles.inlineCritical: false` in `angular.json`): it would add an inline `<script>` to `index.html`. Don't add inline scripts, `eval` or external origins (scripts, fonts, images) without updating the CSP. Inline styles are allowed (Angular's component styles). CI's `docker` job (after `unit` and `build`) builds the image for amd64, fails on fixable HIGH/CRITICAL Trivy findings, checks the user isn't root, and smoke-tests it read-only: the app and a deep link answer, `/api` answers `502` before a stub API exists and reaches the stub once it is up, and the headers above are present.

**Published images** (issue #86, the same setup as build-bro-api#28): only after all of that passes, the same job pushes the tested image (retagged, not rebuilt) to the public package `ghcr.io/esistegalaber/build-bro-ui`: `pr-<N>` for a PR (moves with each push), `main` plus `sha-<7>` for each push to `main`, and `X.Y.Z`, `X.Y` and `latest` for a release. Dependabot and fork PRs get a read-only token, so their image is checked but not published. `docker/metadata-action` makes the tags and the OCI labels (version, revision, created); it would overwrite the description label with the GitHub repo's empty description, so the workflow passes the `Dockerfile`'s text explicitly (keep both in step). Runs are serialised per ref (queued on `main`, cancelled on PRs). `.github/workflows/ghcr-cleanup.yml` (`dataaxiom/ghcr-cleanup-action`) deletes a PR's `pr-<N>` when it closes and, weekly, untagged images and all but the 20 newest `main` `sha-…` images; release tags and `main` are never deleted.

**Releases and the version:** a release is a GitHub release with a tag `vX.Y.Z` on a `main` commit (documented, not enforced). The tag run tests, builds, scans and smoke-tests the tagged commit (the `sonarcloud` job is skipped) and publishes `X.Y.Z`, `X.Y` and `latest` (`latest` not for pre-releases). `package.json` stays at `1.0.0-SNAPSHOT` and is never bumped: nothing in the app reads its version, so the release version lives only in the image tags and the OCI `version` label.
