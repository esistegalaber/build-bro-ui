# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Build Bro UI is an Angular 22 single-page app with NgRx 22, TypeScript 6, Tailwind CSS 4 and daisyUI 5, built with the esbuild-based `application` builder (`ng serve` runs on Vite). The Angular 22 CLI needs Node ^22.22.3, ^24.15 or >=26. Builds and tests are verified on Node 26. It is the frontend for the Build Bro REST API (the sibling repo `../build-bro-api`, Spring Boot on port 8080). It browses builds, build sets, projects, servers and deployments.

## Commands

```bash
npm start              # ng serve on :4200, proxies /api -> http://localhost:8080 (proxy.conf.json)
npm run start-iso      # ng serve without the proxy
npm run build          # production build to dist/build-bro-ui/browser
npm run watch          # development build in watch mode
npm test               # Vitest unit tests in watch mode (`npm test -- --watch=false` once, add `--coverage` for coverage/)
npx ng test --watch=false --include='src/app/builds/**/*.spec.ts'   # a subset of unit specs
npm run cypress:run        # headless e2e tests against the fake API (needs only the app on :4200)
npm run cypress:run:live   # same specs against the real API on :8080 (needs testdata.sql loaded)
npm run cypress:open       # interactive Cypress
npx cypress run --spec cypress/e2e/builds-page.cy.ts   # single e2e spec
npm run cypress:snapshot-api   # regenerate cypress/fixtures/api-db.json from a running API
```

No linter is configured (there is no `ng lint` target and no ESLint). There are no Cypress component specs, even though `cypress.config.ts` has a `component` section. Cypress (16) is pinned to an exact version in `devDependencies` and needs Node 22, 24 or 26+. npm 12 (bundled with Node 26) blocks dependency install scripts unless `package.json` → `allowScripts` approves them. Cypress's binary download is approved there, pinned to its exact version, so **after bumping `cypress`, run `npm approve-scripts cypress`** to move the pin, or `npm ci` skips the download (then `npx cypress install` fetches it by hand; `npx cypress verify` shows whether the binary is there). The other blocked scripts (esbuild, lmdb, msgpackr-extract, @parcel/watcher, fsevents) aren't needed, since they ship prebuilt binaries. The `cypress:run*` scripts run in **Chrome** (`--browser chrome`; Cypress 16 deprecates Electron), so Chrome must be installed wherever the tests run. There are two kinds of tests:

- **Unit tests** (Vitest through Angular's `@angular/build:unit-test` builder, the `test` target in `angular.json`, `tsconfig.spec.json`). They run in Node with jsdom, no browser or backend, in a few seconds. Specs sit next to the code as `*.spec.ts`. They cover the logic layer (reducers, selectors, effects, guards, pipes, `ThemeService`) and the app shell (`AppComponent`, `SideNav`). Other components get unit tests as they are redesigned (epic #44). Component specs set inputs with `fixture.componentRef.setInput(...)`, wait with `await fixture.whenStable()` (zoneless), use `provideMockStore({initialState})` for pages, and find elements by `data-cy-id`. Helpers in `src/testing/`: `setUpEffects()` (effects with `provideMockActions`, `provideMockStore` selectors and `HttpTestingController`), `collect()` (what an effect emits), `API_ERROR`, and small data builders (`someProjects()`, `build()`, …). Test selectors through `.projector(...)`, guards with `TestBed.runInInjectionContext`. Configuring `TestBed` twice in one test fails, so use `it.each` for variations. Vitest globals (`describe`, `it`, `expect`, `vi`) need no imports.
- **e2e tests** (Cypress) in `cypress/e2e/`, one spec per page, for the flows across pages.

**Two e2e modes.** By default, `cypress/support/e2e.ts` installs an in-memory **fake API** (`cypress/support/fake-api.ts`) before every test. It serves `cypress/fixtures/api-db.json`, a snapshot of the real API with `testdata.sql` loaded, and implements search, filtering, sorting (ties by ascending id, like the API), paging and the mutations. Every test gets a fresh copy of the data. Any `/api` call it doesn't stub gets a 501, so **a new endpoint needs a stub in `fake-api.ts`**. Specs use `cy.intercept(...).as(...)` without handlers only to wait on and inspect requests; those fall through to the fake. With `--expose LIVE=true` (`cypress:run:live`) the fake is skipped and the specs call the real API. Cypress 16 removed `Cypress.env()`, so the old `CYPRESS_LIVE=true` and `--env LIVE=true` are **silently ignored** and the run stays on the fake API. The tests that change data clean up after themselves, so live mode can be re-run on the same database. When `testdata.sql` changes, reload it into the DB and run `cypress:snapshot-api`. `cypress/tsconfig.json` sets `"outDir": null`: Cypress's webpack preprocessor compiles each spec on its own, and with the app's inherited `outDir` TypeScript 6 demands an explicit `rootDir` (TS5011). Cypress never emits files, so it needs no `outDir`.

CI runs on GitHub Actions (`.github/workflows/build.yml`, on pushes to `main` and on PRs). It has three jobs on Node 26. **Unit tests** (`npm ci --ignore-scripts`, then the unit tests with coverage) uploads `coverage/build-bro-ui/lcov.info` as an artifact. In parallel, **Build and e2e tests** runs `cypress-io/github-action`: `npm ci`, `npm run build`, `npm start`, then the specs in Chrome against the fake API, with no backend or database. **SonarCloud** waits only for the unit tests (it also runs when they fail). It is a SonarCloud scan (`sonarqube-scan-action`, configured by `sonar-project.properties`, needs the `SONAR_TOKEN` secret). It reads that coverage report. The quality gate wants 80% coverage on new code, so new logic needs unit tests. SonarCloud analyzes the whole repository (its analysis scope ignores `sonar.sources`/`sonar.tests`; only exclusions work), so `sonar-project.properties` excludes `src/**/*.spec.ts` and `src/testing/` from the analysis, and leaves the Cypress suite (`cypress/**`, `cypress.config.ts`) and files without logic (`main.ts`, environments, `*.routes.ts`, `*.actions.ts`, the same list as `coverageExclude` in `angular.json`) out of coverage. A new file that isn't app code needs to be added there, or it counts as uncovered code. The SonarCloud project uses CI-based analysis, so its "Automatic Analysis" must stay off, or the scan fails. Elements are selected with `data-cy-id` attributes, so keep them when editing templates.

## Architecture

- **Standalone components, no NgModules.** Standalone is the default since Angular 19, so components and pipes don't declare `standalone: true`. The compiler warns about components in `imports` that a template doesn't use, so remove those. `src/main.ts` bootstraps `AppComponent` with `bootstrapApplication`. The app is **zoneless** (`provideZonelessChangeDetection()`; there is no `zone.js`). Change detection runs only after template events, `async` pipe emissions, signal changes or `markForCheck()`, not after timers or plain subscriptions. So keep state flowing through the store and the `async` pipe. Buttons inside a `<form>` need an explicit `type`. A button without one is a submit button: it also fires the form's `(submit)` right after its `(click)`, before change detection has passed new inputs to the form. It also registers the root store slices (`alert`, `stats`, `nav`, `projects`, `servers`), their effects and the store devtools with NgRx's standalone providers (`provideStore`, `provideEffects`, `provideStoreDevtools`). There are no NgModule imports (`importProvidersFrom`) and no Angular animations. `app.routes.ts` lazy-loads one `*.routes.ts` per feature folder. Dependencies are injected with `inject()` in field initializers (`private store = inject<Store<Buildz>>(Store)`), not constructor parameters. Declare them above the fields that use them, such as `createEffect(() => this.actions$...)` in effects or `this.store.pipe(...)` in pages.
- **Feature folders** (`builds/`, `build-sets/`, `build-set-edit/`, `deployments/`, `projects/`, `servers/`, `home/`) follow this pattern, though not every folder has every part. `projects/`, `servers/` and `home/` have no `state/` and read the root slices (`projects`, `servers`, `stats`). `build-sets/` has no `ui/` and uses `src/app/ui/build-sets/`.
  - `*.page.ts` is the routed container component. It selects from the store and dispatches actions.
  - `ui/` holds presentational components with `@Input`/`@Output`.
  - `state/` holds the NgRx actions, reducer, selectors and effects. These are registered **lazily in the feature's route `providers`** via `provideState(FEATURE_X, reducer)` / `provideEffects(XEffects)` (see `builds/builds.routes.ts`), not in `main.ts`.
- **App shell** (`app.component.ts`): the side nav (`ui/nav/side.nav.ts`: logo, main navigation with the active page marked via `aria-current`, theme switch; it collapses to icons, state in the `nav` slice) next to a centred content column (max 1120 px) with the alert panel above the routed page. On narrow screens the side nav wraps above the content.
- **Shared code**: `src/app/ui/` holds presentational components reused across features (accordions, paginator, nav, alert panel). Pages start with `bb-page-header` (the edit page has its own header with a breadcrumb in `build-set-name.form.ts`) (`heading`, `description`, actions as content), says "nothing here" with `bb-empty-state` (`icon`, `framed` for a dashed box on the page, `compact` for side panels; message and button as content) and shows `bb-loading` while data is on its way. Use them instead of repeating the markup. `src/app/core/` holds the shared model interfaces (`core/state/model.ts`), root-level state slices and pipes. Import shared things through the `core/index.ts` barrel.
- **HTTP lives only in effects** (and some route guards). They call relative `/api/v1/...` URLs with `HttpClient` (`provideHttpClient(withXhr())` keeps the XHR backend, since Angular 22 defaults to `fetch`), and failures map to `AlertActions.backendErrorOccurred`. The global alert reducer reads the backend's error shape (`error.message` / `error.description`, from the API's `IExceptionInfo`).
- **Route guards load data**: in `build-set-edit`, the `new` / `:build-set-name` / `clone/:build-set-name` guards (`guards/*.guard.ts`) dispatch load actions and always return `true`; `build-sets.routes.ts` does the same for the build set names. Guards are functional `CanActivateFn`s that use `inject(Store)`, not classes (class guards are deprecated).
- **Templates are inline** and use the built-in control flow (`@if`, `@for`), not `*ngIf`/`*ngFor`. Track `@for` loops over objects by a stable key (`track build.id`, `track buildTemplate.project.id`, `track label.key` for `keyvalue`), not by the object itself. Store updates and the `deepClone` pipe always create new objects, so tracking by identity rebuilds every row on each update. That logs NG0956 in dev mode and loses DOM state. With a stable key, Angular reuses the row's components and only passes in new `@Input`s, so those components must render from their inputs and not keep their own copies. Loops over plain strings can use `track name`. They are styled with Tailwind utility classes plus daisyUI component classes. Tailwind 4 is configured in CSS, not in a `tailwind.config.js`. Angular's builder runs it through PostCSS (`.postcssrc.json` → `@tailwindcss/postcss`), and Tailwind finds the classes in the inline templates on its own. `src/styles.css` holds the whole setup:
  - The `@import`s come first (Material Icons, then the Inter, Plus Jakarta Sans and JetBrains Mono variable fonts from `@fontsource-variable/*`), because browsers ignore an `@import` after other rules. The fonts are bundled, so there are no external font requests. `@theme` maps them to `font-sans` (text, the default), `font-display` (headings; `h1`–`h3` use it automatically) and `font-mono` (build numbers, hashes).
  - `@plugin 'daisyui' { themes: false; }` turns off daisyUI's built-in themes, and three `@plugin 'daisyui/theme'` blocks define ours: **light** (default), **dark** and **lagoon** (the custom theme). Keep them in sync with `THEMES` in `core/theme.service.ts`. Colors: page background `base-200`, cards `base-100`, borders `base-300`. **Projects are never color-coded** (setups can have dozens of them); color only marks state: tests ok/broken, pinned builds, selection.
  - `ThemeService` (`core/theme.service.ts`) sets `data-theme` on `<html>` and remembers the choice in `localStorage` (wrapped in try/catch; it falls back to light). The theme switch is at the bottom of the side nav.
  - A small override keeps daisyUI's `.collapse` (the accordions) visible. Tailwind 4's `collapse` utility (`visibility: collapse`) would otherwise win over it.

  daisyUI 5 defaults that differ from daisyUI 2:
  - A plain `btn` is light grey; add `btn-neutral` for the dark buttons used throughout the app.
  - Inputs and selects are bordered without `input-bordered`/`select-bordered`.
  - Button groups are `join` + `join-item`, and the selected menu entry is `menu-active`.
  - `form-control` and `label-text` no longer exist (use `flex flex-col` and `text-sm`).
  - Tailwind 4's `border` uses the current text color, so give borders a theme color such as `border-base-content/20`. Components use `OnPush` change detection (the default since Angular 22; the two components that never set a strategy were given `ChangeDetectionStrategy.Eager`, the pre-22 default). Store values are often passed through the `deepClone` pipe (`CloningPipe`) before reaching forms, so forms never mutate frozen store state.
- Model interfaces in `core/state/model.ts` mirror the API DTOs (`IBuild`, `IBuildSearchResult`, …). Keep them in sync with `build-bro-api`'s `api.model` package.

## Deployment

The `Dockerfile` packages a prebuilt `dist/build-bro-ui/browser` into nginx, so run `npm run build` first. `default.conf.template` proxies `/api` to `http://${BUILDZ_API}:8080/api` (env var `BUILDZ_API`, default `api`) and falls back to `index.html` for SPA routing.
